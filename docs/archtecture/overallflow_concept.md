本プロジェクトの根幹であるAIチェックの処理フローの概要を以下に示す

# 業務フロー（本プロジェクトを利用するユーザ目線）
1. チェックリスト（csv形式）、レビュー設定（json形式）、レビュー実行時のskillsを準備する
2. 本プロジェクトの`.ci-template/piplines/template.yml`を`.gitlab-ci.yml`上で`include`する
  - チェックリスト、レビュー設定、レビュー実行時のskillsのパスを環境変数で指定する
3. 初回MR作成時はMRのdiffが存在する場合にチェックが実行され、チェック結果に関するコメントが投稿される
  - コメントにはMarkdown表形式のチェック結果（チェック項目、評定、コメント）と最新のコミットハッシュが合わせて表示されている
    - 表については15項目超えた場合は折りたたみ形式（details,summaryタグ）で表示されている
    - エラーになった場合は、評定欄に「エラー」、コメント欄にエラーメッセージが表示されている
4. MR更新前に、前回のチェック結果を前提にレビューさせたくない場合はそのチェック結果を含むコメントを削除する
5. MR更新時は前回チェック結果がコメントに含まれていた場合は、そのチェック結果を前提にレビューされる

# システム処理フロー
0. ワークフロー開始前の事前処理
  - 最新チェック結果の取得
    - MRのコメント履歴から過去のチェック履歴があるか確認し、存在した場合は最新のチェック結果を取得する
      - ただし、チェック結果に紐づくチェックリストと今回チェックするチェックリストを比較して、後者に含まれない履歴は削除しておく
  - 最新チェック結果から今回チェック時点までの履歴取得
    - 最新チェック結果を取得できた場合は、以下を取得する
      - その結果を取得した時点以降のコミットメッセージ一覧
      - その結果を取得した時点から今回チェック時点までのdiff
  - レビュー設定、チェックリストの取得
1. チェックリスト分割
  - ユーザが指定した同時レビュー項目数ごとにチェックリストを分割する
    - チェックリスト全体をAgentに読み込ませ、類似のチェック項目をグルーピングする
      - チェック項目には1始まりの連番IDが付与されており、AgentはIDで項目を特定する（コンテキスト効率化・内容不一致防止のため）
    - Agentの出力結果は完全に同時レビュー項目数で分割される保証はないので、最終的に過不足なくグルーピングさるように調整する（あくまで過不足なく分割することが目的なので、機械的に調整して良い）
2. チェック実行
  - 1で分割したチェック項目のグループごとにAIによるチェックを実行する（並列度: 5）
    - プロジェクトのルートフォルダを起点としたmastra workspaceの機能を搭載したAgentがチェックを実行し、チェック項目ごとにレビュー結果を判定する
      - Agentには以下の様なプロンプトを与える
        - systemプロンプト
          - レビュー実行の方針や注意点
            - MRレビューのスペシャリストとして振る舞うこと
            - 与えられたMR全体diffをレビューすること
              - diffのみではレビューが難しく、コードベースの調査が必要であればworkspaceやsandboxのtool(mastra_workspace_~のtool)を利用してコードベースを調べること
            - 過去のチェック結果を最大限活用して効率的にレビューすること（存在した場合のみプロンプトに記載）
            - レビュー対象の全てのチェック項目
            - チェック項目のレビューが完了した際は、レビュー結果格納tool（後述）を利用すること
              - 全てのチェック項目のレビューが完了するまで処理を終了しないこと
        - userプロンプト
          - MRの情報（タイトル、説明、ブランチ情報等）
          - MR全体のdiff
          - レビュー対象チェック項目に紐づく最新のチェック結果とその結果取得時点から今回チェック時点までのコミットメッセージ一覧とdiff（存在した場合のみプロンプトに記載）
      - Agentは与えられてたプロンプトに従って、mastra workspaceで利用可能なtoolを活用しながら自律的にレビューを実行する
        - 例えばsandbox toolsを利用すれば生のgitコマンドやGitLab API実行により意義ある分析ができるはず
          - ユーザに指定されたskillsを利用しながら作業を実施する
        - チェック項目には1始まりの連番IDが付与されており、レビュー結果格納時はIDで項目を特定する（コンテキスト効率化・内容不一致防止のため）
        - レビュー結果はjsonファイルで管理する
          - Agentにはレビュー結果を格納できるtool（+実行済みのレビュー結果一覧を確認できるtool）を与える
            - 複数Agentが同時にレビュー結果格納toolを利用する場合もあるので、排他制御できる様にする
          - Agentの処理が完了するごとに全てのレビュー結果が格納されているか確認し、漏れているチェックリストが存在した場合はその旨をAgentに伝えて残りのチェックリストに関するチェックを実行させる
            - つまり、Agentが過去のメッセージ履歴を保持しておく必要があるので注意
3. コメント投稿
  - 2でチェックリスト内のチェック項目全てのチェックが完了した後に、チェック結果と今回チェック時点のコミットハッシュをまとめてMRのコメントに投稿する

## エラーハンドリング
チェック実行中のエラーは種別に応じて処理される:
- コンテキスト長エラー: 作業履歴を要約Agentで要約し、新しいスレッドでレビューを継続する（最大3回ループ）
- API呼び出しエラー: レビュー結果表に実際のエラー内容を表示する
- その他のエラー: レビュー結果表に「予期せぬエラー（実行ログを確認してください）」を表示する
- いずれの場合も、既にストア済みの成功結果は保持される（部分成功を失わない）

## 実装方針
1,2についてはmastra workflowで実装する
