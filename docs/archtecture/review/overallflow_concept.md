review 機能（AI MRレビュー）の処理フロー概要を以下に示す

# 業務フロー（本プロジェクトを利用するユーザ目線）
1. チェックリスト（csv形式）、レビュー設定（json形式）、レビュー実行時のskillsを準備する
2. 本プロジェクトの`.ci-template/pipelines/template.yml`を`.gitlab-ci.yml`上で`include`する
  - チェックリスト、レビュー設定、レビュー実行時のskillsのパスを環境変数で指定する
3. 初回MR作成時はMRのdiffが存在する場合にチェックが実行され、チェック結果に関するコメントが投稿される
  - コメントにはチェック結果と最新のコミットハッシュが合わせて表示されている
    - レビュー設定の`reviewCommentLayout`で出力レイアウトを選択できる
      - `table`（デフォルト）: Markdown表形式（チェック項目、評定、コメント）
      - `sections`: 「#、チェック項目、評定」のサマリ表＋その下にチェック項目ごとの折りたたみ（タイトル`#<番号>`）で詳細を表示。詳細はエスケープされないため表のネストや見出しが利用できる
    - `table`では表示件数が折りたたみ閾値（`FOLD_THRESHOLD`=2）を超えた場合に表全体が折りたたみ形式（details,summaryタグ）で表示される（`sections`は件数によらず項目ごとに折りたたむ）
    - エラーになった場合は、評定に「エラー」、コメントにエラーメッセージが表示されている
    - チェックリストCSVのうちコメントに表示する列は`CHECKLIST_DISPLAY_COLUMNS`で絞り込める（AIへの指示に使う列とは独立）
4. MR更新前に、前回のチェック結果を前提にレビューさせたくない場合はそのチェック結果を含むコメントを削除する
5. MR更新時は前回チェック結果がコメントに含まれていた場合は、そのチェック結果を前提にレビューされる
6. パイプラインをリトライした場合（新しいコミットなし）、前回成功したレビュー結果はそのまま再利用され、エラーだった項目や結果がない項目のみ再レビューされる

# システム処理フロー

## 構成パターン
- **ローカルモード**（`AI_API_KEY`、`AI_API_ENDPOINT_URL`、`AI_MODEL_NAME`が全て設定されている場合）: CLIが全処理をローカルで実行する（開発用・後方互換）
- **APIモード**（上記3変数のいずれかが未設定の場合）: CI/CDジョブのCLIが外部APIサーバー（`AIKATA_API_URL`）にSSEでレビュー実行を委譲し、コメント投稿・品質ゲート評価はCLI側で実行する。AI APIキーはAPIサーバー側で一元管理（流出リスク排除）。認証はGitLab CI/CDの`id_tokens`（JWT）で行う。`AIKATA_API_URL`と`AIKATA_JWT`が必要

以下のフローはローカルモードを基準に記述。APIモードではステップ0〜2がAPIサーバー側で実行され、SSEで結果がCLIに返却される。ステップ3（コメント投稿）および品質ゲート評価はいずれのモードでもCLI側で実行される。

0. ワークフロー開始前の事前処理
  - MR diffの取得（ローカルgit優先）
    - MR diffはローカルgitリポジトリ（`git diff`）から優先取得する
      - CI/CD環境では事前に `git fetch --unshallow` と `git fetch origin <targetBranch>` を実行してgit履歴を確保する
    - ローカルgit取得が失敗した場合はGitLab API（`access_raw_diffs=true`）にフォールバック
    - 両方失敗した場合はエラー終了
    - インクリメンタルdiff（前回レビュー以降の差分）も同様にローカルgit優先
  - 最新チェック結果の取得
    - MRのコメント履歴から過去のチェック履歴があるか確認し、存在した場合は最新のチェック結果を取得する
      - ただし、チェック結果に紐づくチェックリストと今回チェックするチェックリストを比較して、後者に含まれない履歴は削除しておく
  - 最新チェック結果から今回チェック時点までの履歴取得
    - 最新チェック結果を取得できた場合は、以下を取得する
      - その結果を取得した時点以降のコミットメッセージ一覧
      - その結果を取得した時点から今回チェック時点までのdiff
  - レビュー設定、チェックリストの取得
1. チェックリスト分割
  - ユーザが指定した同時レビュー項目数ごとにチェックリストを分割する
    - チェックリスト全体をAgentに読み込ませ、類似のチェック項目をグルーピングする
      - チェック項目には1始まりの連番IDが付与されており、AgentはIDで項目を特定する（コンテキスト効率化・内容不一致防止のため）
    - Agentの出力結果は完全に同時レビュー項目数で分割される保証はないので、最終的に過不足なくグルーピングさるように調整する（あくまで過不足なく分割することが目的なので、機械的に調整して良い）
2. チェック実行
  - 1で分割したチェック項目のグループごとにAIによるチェックを実行する（並列度: 5）
    - プロジェクトのルートフォルダを起点としたmastra workspaceの機能を搭載したAgentがチェックを実行し、チェック項目ごとにレビュー結果を判定する
      - Agentには以下の様なプロンプトを与える
        - systemプロンプト
          - レビュー実行の方針や注意点
            - MRレビューのスペシャリストとして振る舞うこと
            - 与えられたMR全体diffをレビューすること
              - diffのみではレビューが難しく、コードベースの調査が必要であればworkspaceやsandboxのtool(mastra_workspace_~のtool)を利用してコードベースを調べること
            - 過去のチェック結果を最大限活用して効率的にレビューすること（存在した場合のみプロンプトに記載）
            - レビュー対象の全てのチェック項目
            - チェック項目のレビューが完了した際は、レビュー結果格納tool（後述）を利用すること
              - 全てのチェック項目のレビューが完了するまで処理を終了しないこと
        - userプロンプト
          - MRの情報（タイトル、説明、ブランチ情報等）
          - MR全体のdiff
          - レビュー対象チェック項目に紐づく最新のチェック結果とその結果取得時点から今回チェック時点までのコミットメッセージ一覧とdiff（存在した場合のみプロンプトに記載）
      - Agentは与えられてたプロンプトに従って、mastra workspaceで利用可能なtoolを活用しながら自律的にレビューを実行する
        - 例えばsandbox toolsを利用すれば生のgitコマンドやGitLab API実行により意義ある分析ができるはず
          - ユーザに指定されたskillsを利用しながら作業を実施する
        - チェック項目には1始まりの連番IDが付与されており、レビュー結果格納時はIDで項目を特定する（コンテキスト効率化・内容不一致防止のため）
        - プロジェクト内に画像ファイル（PNG, JPEG, GIF, WebP）が含まれる場合は、readImageツールが登録され、Agentは画像ファイルをマルチモーダルに読み取って分析できる
          - readImageツールは画像データをbase64エンコードしてRequestContextに蓄積し、prepareStepフックでMastraDBMessage（FileUIPart形式）としてメッセージ列に注入する
        - レビュー結果はjsonファイルで管理する
          - Agentにはレビュー結果を格納できるtool（+実行済みのレビュー結果一覧を確認できるtool）を与える
            - 複数Agentが同時にレビュー結果格納toolを利用する場合もあるので、排他制御できる様にする
          - Agentの処理が完了するごとに全てのレビュー結果が格納されているか確認し、漏れているチェックリストが存在した場合はその旨をAgentに伝えて残りのチェックリストに関するチェックを実行させる
            - つまり、Agentが過去のメッセージ履歴を保持しておく必要があるので注意
3. コメント投稿
  - 2でチェックリスト内のチェック項目全てのチェックが完了した後に、チェック結果と今回チェック時点のコミットハッシュをまとめてMRのコメントに投稿する
  - チェック結果の突合キー（AI用のチェック項目content）と評定はコメント内のメタデータ（HTMLコメント）に格納する
    - 表示部分（表／セクション）は表示専用となり、再レビュー時のチェック項目・評定の復元はメタデータから行う
    - コメント本文は文字数の二重化を避けるためメタデータに持たず、表示部分から順序対応で復元する
      - sectionsレイアウトはコメント本文を区切りマーカーで囲んで無損失に復元する
      - 表示されない非表示結果のみ、コメント本文もメタデータに格納する
    - 旧フォーマットのコメント（メタデータにコメント本文を持つ／メタデータに可視結果を持たない）も
      従来どおり復元できる（後方互換）

## エラーハンドリング
チェック実行中のエラーは種別に応じて処理される:
- コンテキスト長エラー: 作業履歴を要約Agentで要約し、新しいスレッドでレビューを継続する（最大3回ループ）
- API呼び出しエラー: レビュー結果表に実際のエラー内容を表示する
- その他のエラー: レビュー結果表に「予期せぬエラー（実行ログを確認してください）」を表示する
- いずれの場合も、既にストア済みの成功結果は保持される（部分成功を失わない）

## サジェスト処理フロー

suggest有効時（suggestEnabledRatingLabelsが空でない場合）に以下の処理が追加される。

### 事前処理（ReviewExecutionService）
1. MRの既存ディスカッションからaikataマーカー付きのsuggest discussionを取得する（getSuggestDiscussions）
2. 取得したsuggest discussionを以下に分類する:
   - **activeSuggests**: unresolve & 現在のチェックリスト内 & diff未更新 → Agentに提供し、同じ内容のsuggest生成を抑止する
   - **suggestsToResolve**: diff更新済みまたはチェックリスト外 → コメント投稿時に自動resolveする
3. activeSuggestsをあらかじめsuggestストアに登録する

### チェック実行時（reviewAgent）
- suggest有効時にAgentに追加で与える情報:
  - systemプロンプト: 指定評定のチェック項目に対して具体的なsuggestを生成する役割・注意文言、以前の有効なsuggestと重複しないこと、最終的にチェック結果とsuggest内容を確認すること
  - userプロンプト: diffの内容
  - tools:
    - **getDiffDetail**: diff上の特定ファイル・行範囲の詳細を取得
    - **storeSuggest**: suggest情報を登録（filePath, originalCode, suggestedCode, comment等をinput schemaで受け取り、バリデーション・重複チェックを実施）
    - **getSuggests**: 登録済みsuggest一覧を取得（以前の有効なsuggest含む）

### コメント投稿時（CommentPostingService）
1. suggestsToResolveに該当するsuggest discussionをGitLab APIでresolveする
2. 新規suggestのoriginalCodeをMR diffから検索し、行番号を解決する（ResolvedSuggestion）
3. 解決済みsuggestをGitLab MRにdiff discussionとして投稿する（GitLabのsuggest記法を使用）
4. 行番号解決に失敗したsuggestはスキップし、警告ログを出力する
