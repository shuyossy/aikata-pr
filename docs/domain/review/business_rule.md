# ビジネスルール
記載フォーマット
```
- ビジネスルール名
  - 目的/背景
    - [箇条書き]
  - 条件
    - [条件(ルール内容)を箇条書き]
  - 結果(アクション)
    - [箇条書き]
  - 関連するユースケースorエンティティ:
```
---

- チェックリスト分割ルール
  - 目的/背景
    - チェック項目を効率的にレビューするため、類似項目をグルーピングする
  - 条件
    - 同時レビュー項目数がnullの場合、全項目を1グループにする（分割しない）
    - 同時レビュー項目数が1の場合、各項目を個別グループにする
    - 同時レビュー項目数が総項目数以上の場合、全項目を1グループにする
    - 上記以外でAI分割が成功した場合、AI分割結果を調整して使用
    - AI分割が失敗した場合、機械的分割にフォールバック
  - 結果(アクション)
    - CheckItem[][]（分割されたグループ）
  - 関連するユースケースorエンティティ: Checklist, CheckItem, checklistSplitStep

- AI分割結果の調整ルール
  - 目的/背景
    - AI分割結果が不正確な場合でも正しいグループ分けを保証する
  - 条件
    - 重複項目は除去する
    - 漏れ項目は補完する
    - グループサイズ超過時は再分割する
    - 最終的にconcurrentReviewCount未満のグループは最後のグループのみ許容
  - 結果(アクション)
    - 正規化されたCheckItem[][]
  - 関連するユースケースorエンティティ: checklistSplitStep

- レビュー結果格納ルール
  - 目的/背景
    - 複数のエージェント実行が並行してレビュー結果を蓄積するため
  - 条件
    - 同じチェック項目IDの結果は上書きされる
    - ファイルロックによる排他制御を行う
  - 結果(アクション)
    - JSONファイルへの永続化
  - 関連するユースケースorエンティティ: storeReviewResultTool

- 前回レビューコンテキスト構築ルール
  - 目的/背景
    - 再レビュー時に前回の結果を考慮するため
  - 条件
    - MRコメントからaikataマーカーを持つ最新のコメントを検索
    - レビュー結果の復元はコメント内メタデータ（aikata-review-data）を優先する
      - メタデータに可視結果（visibleResults）が含まれる場合はそこから復元する
        - コメント本文はメタデータに含まれないため、コメントの表示部分から順序対応で復元する
        - 旧フォーマットとしてメタデータにコメント本文が含まれる場合はそちらを優先する
      - 含まれない場合（旧フォーマットのコメント）はMarkdownテーブルをパースして復元する
    - 前回結果のうちエラーになった項目は除外し、今回のチェックリストに含まれる項目のみフィルタ
    - 前回レビュー以降のコミットとdiffを取得
  - 結果(アクション)
    - PriorReviewContext | null
  - 関連するユースケースorエンティティ: ReviewExecutionService, CommentParser

- レビュー結果メタデータ格納ルール
  - 目的/背景
    - コメントの表示レイアウトを変更しても前回レビュー結果を正しく復元できるようにするため
    - 表示用に変換されたチェック項目テキストからはAI用フォーマットのcontentを復元できないため
    - 一方で、表示部分から復元できる情報をメタデータにも持つとコメントの文字数が二重になるため
  - 条件
    - メタデータには「表示部分から復元できない情報」のみを格納する
    - 可視結果はcheckItemContentと評定ラベルのみを格納し、コメント本文は格納しない
      - コメント本文は表示部分から復元する（メタデータと表示部分の並び順は常に一致する）
      - sectionsレイアウトではコメント本文を区切りマーカー（aikata-c）で囲み、
        生Markdownのまま無損失に復元できるようにする
      - tableレイアウトではコメント列のセルから復元する（セルエスケープの復元を伴う）
    - 非表示結果は表示部分を持たないため、コメント本文もメタデータへ格納する
    - メタデータに格納するcheckItemContentは表示用ではなくAI用の生contentとする（突合キーであるため）
    - エラー結果は評定ラベル「エラー」として格納する（コメント本文にエラーメッセージが入る）
  - 結果(アクション)
    - Markdownテーブル/セクションは表示専用となり、レイアウトを自由に変更できる
    - コメント本文がコメント内で二重化しない
  - 関連するユースケースorエンティティ: CommentFormatter, CommentParser

- レビューコメントレイアウトルール
  - 目的/背景
    - Markdownテーブルのセル内では横幅が狭く、表のネストもできないため詳細が読みづらい
  - 条件
    - reviewCommentLayoutが'table'の場合（デフォルト）
      - 「チェック項目・評定・コメント」の3列テーブルで出力する（従来形式）
      - セル内のパイプと改行はエスケープする
    - reviewCommentLayoutが'sections'の場合
      - 「#・チェック項目・評定」のサマリテーブルを出力する（#は表示対象の結果に振る1始まりの連番）
      - サマリテーブルの下に、チェック項目ごとの折りたたみ（details,summaryタグ）を件数によらず出力する
        - 折りたたみのタイトルは`#<番号>`とし、サマリテーブルの#列と対応させる
        - 折りたたみの中身は「表示用チェック項目（`<列名>`と値を改行して列挙）＋評定（`**評定: X**`）＋コメント本文」とする
        - コメント本文はエスケープせず生Markdownとして出力する（表・見出し・箇条書きが利用可能）
    - 'table'では、表示対象の件数が折りたたみ閾値を超えた場合にテーブル全体を折りたたみ（details,summaryタグ）で表示する
    - いずれのレイアウトでも、表示用チェック項目の山括弧（`<` `>`）はHTMLタグとして解釈されないようエスケープする
  - 結果(アクション)
    - MRコメント本文のMarkdown
  - 関連するユースケースorエンティティ: ReviewSettings, CommentFormatter, CommentPostingService

- チェック項目表示列ルール
  - 目的/背景
    - AIへの指示は詳細にしつつ、レビュー結果上の表示は簡潔にしたいため
  - 条件
    - 表示用の列が指定された場合、その列のみをチェックリストCSVから抽出して表示用テキストを生成する
    - 表示用の列が指定されない場合、AI指示用の列（チェックリスト抽出列）と同じ列を使用する（従来と同一表示）
    - 表示用テキストの生成方法はAI指示用と同じ（ヘッダ付き構造化フォーマット、1列指定かつヘッダ除外時は値のみ）
    - 表示用テキストはコメント表示にのみ使用し、AIへの指示・結果の突合キーには使用しない
  - 結果(アクション)
    - チェック項目のAI用contentと表示用contentの対応表
  - 関連するユースケースorエンティティ: ChecklistParser, CommentFormatter, SuggestCommentFormatter

- エラー分類ルール
  - 目的/背景
    - レビュー実行時のエラーを種別に応じて適切に処理するため
  - 条件
    - Agentによるレビュー漏れ: Agentが正常終了したが結果が格納されなかった場合
    - コンテキスト長エラー: APICallError.responseBodyにコンテキスト長超過を示すパターンが含まれる場合
    - API呼び出しエラー: エラーチェーンにAPICallErrorが含まれる場合（コンテキスト長エラーを除く）
    - その他のエラー: 上記以外
  - 結果(アクション)
    - Agentによるレビュー漏れ: レビュー結果表に「本チェック項目のレビューが完了しませんでした。再度実行してください」を表示
    - コンテキスト長エラー: 作業履歴を要約して処理を継続
    - API呼び出しエラー: レビュー結果表にエラー内容を表示。エラー詳細をログに出力
    - その他のエラー: レビュー結果表に「予期せぬエラー（実行ログを確認してください）」を表示。エラー詳細をログに出力
    - いずれの場合も、既にストア済みの成功結果は保持する
  - 関連するユースケースorエンティティ: executeReview, classifyError

- コンテキスト長リカバリールール
  - 目的/背景
    - MRレビューがヘビーな場合にコンテキスト長エラーが発生する可能性があるため、作業を継続できるようにする
  - 条件
    - コンテキスト長エラーを検知した場合
    - 最大3回まで要約→継続をループする
  - 結果(アクション)
    - メモリから会話履歴を取得し、要約Agentで要約する
    - 旧スレッドを削除し、新しいスレッドで要約を踏まえたレビューを継続する
    - 継続プロンプトは「通常のuserプロンプト＋レビュー済み項目＋要約の旨＋要約内容」で構成する
  - 関連するユースケースorエンティティ: executeReview, recoverFromContextLength, summarizationAgent

- パイプラインリトライ時のレビュー最適化ルール
  - 目的/背景
    - CI/CDパイプラインのリトライ時（新しいコミットなし）に、前回成功したレビュー結果を再利用する
  - 条件
    - 前回のaikataレビューコメントのコミットハッシュと今回のMRの最新コミットハッシュが一致する場合をリトライと判定
    - 前回の成功結果（今回のチェックリストに含まれるもの）はそのまま保持
    - 前回エラーだった項目 + 今回のチェックリストにあるが前回結果にない項目のみ再レビュー
    - 再レビュー対象が0件の場合、前回の成功結果をそのまま再投稿
  - 結果(アクション)
    - 保持された結果と新規レビュー結果をチェックリスト順でマージして返却（コメント投稿はCommentPostingServiceが担当）
  - 関連するユースケースorエンティティ: ReviewExecutionService

- 品質ゲートルール
  - 目的/背景
    - レビュー結果に基づいてパイプラインの成否を制御するため
  - 条件
    - 品質ゲートが設定されている場合（failureCriteriaが空でない）
    - 各基準について、非エラーのレビュー結果の評定ラベルごとのカウントを集計
    - いずれかの基準で count >= threshold の場合、品質ゲート失敗（OR条件）
    - エラー結果（isError=true）は評価から除外
    - 非表示評定ラベル（hiddenRatingLabels）の結果も評価対象（hiddenRatingLabelsは表示制御のみ）
  - 結果(アクション)
    - 品質ゲート失敗時: レビューコメントを投稿した後（警告メッセージを付加）、ジョブを失敗（exit code 1）として終了
    - 品質ゲート成功時（または未設定時）: 通常通りジョブ成功として終了
  - 関連するユースケースorエンティティ: QualityGate, ReviewSettings, reviewサブコマンドのエントリ（src/cli/review/index.ts）

- コメント投稿方法ルール
  - 目的/背景
    - 解決すべき指摘がない場合にディスカッション（スレッド）として残るのは不適切なため、投稿方法を分ける
  - 条件
    - 全てのレビュー結果が非エラーかつ非表示評定ラベル（hiddenRatingLabels）に該当する場合
  - 結果(アクション)
    - 該当する場合: GitLab Notes API（通常コメント）として投稿する
    - 該当しない場合: GitLab Discussions API（ディスカッション）として投稿する
    - GitLab Discussions APIはNotes APIで投稿したコメントも返すため、前回レビューコンテキスト構築への影響はない
  - 関連するユースケースorエンティティ: ReviewResult, CommentPostingService, MrDiscussionGateway

- 全レビュー結果エラー時のジョブ失敗ルール
  - 目的/背景
    - CI/CDジョブとしてレビューが全て失敗した場合はジョブ失敗として扱う必要がある
  - 条件
    - レビュー実行の結果、全てのチェック項目のレビュー結果がエラーである場合
    - 結果が0件の場合はエラーとは見なさない
  - 結果(アクション)
    - コメントを投稿せず、ジョブを失敗（exit code 1）として終了する
  - 関連するユースケースorエンティティ: ReviewResult, reviewサブコマンドのエントリ（src/cli/review/index.ts）

- 画像ファイル読み取りルール
  - 目的/背景
    - レビュー対象プロジェクト内の画像ファイルをAIが視覚的に分析できるようにするため
  - 条件
    - プロジェクトのfolderTreeに画像ファイル（PNG, JPEG, GIF, WebP）が含まれる場合のみ、readImageツールを登録しプロンプトで言及する
    - 読み取り可能な形式: PNG, JPEG, GIF, WebP
    - 読み取り不可能な形式の場合は、エラーメッセージとサポート形式一覧を返す
    - ファイルパスはプロジェクトルートからの相対パスで指定
    - プロジェクトディレクトリ外へのパス走査は拒否
  - 結果(アクション)
    - 画像データをbase64エンコードしてRequestContextに蓄積し、prepareStepフックでMastraDBMessage（FileUIPart形式）としてメッセージ列に注入する
  - 関連するユースケースorエンティティ: readImageTool, reviewAgent

- 画像対応コンテキスト長リカバリールール
  - 目的/背景
    - 画像読み取りを含むレビューセッションでコンテキスト長エラーが発生した場合、画像情報を適切に要約に含めるため
  - 条件
    - 通常のコンテキスト長エラー: シリアライズテキストに画像リンク（[Image: path]）を埋め込み、画像実体はimageメッセージとして要約Agentに送信。要約Agentのsystemプロンプトでも画像参照について言及する
    - 許容画像数超過エラー（isContextLengthErrorかつresponseBodyに'images'を含む）: 画像データを除外し、ファイル名のみ使用。除外理由をAgentに通知。要約Agentのsystemプロンプトでは画像参照について言及しない
    - 要約対象に画像が含まれない場合: 既存動作と同じ。要約Agentのsystemプロンプトでは画像参照について言及しない
  - 結果(アクション)
    - 要約Agentが画像を含むコンテキストを適切に要約し、レビュー継続を可能にする
  - 関連するユースケースorエンティティ: contextLengthRecovery, summarizationAgent

- サジェスト有効化ルール
  - 目的/背景
    - 指定した評定結果だったチェック項目に対してコード変更提案（suggest）を生成するため
  - 条件
    - suggestEnabledRatingLabelsで有効化する評定ラベルを配列で指定する（デフォルト: ['C']）
    - 空配列の場合はsuggestを無効にする
    - suggestEnabledRatingLabelsの各ラベルはratingsに存在するラベルのみ指定可能（存在しないラベルが指定された場合はエラー）
  - 結果(アクション)
    - suggestが有効な場合、該当評定のチェック項目に対してAgentがsuggestを生成する
  - 関連するユースケースorエンティティ: ReviewSettings, reviewAgent

- サジェスト重複排除ルール
  - 目的/背景
    - 同一セッション内で同一箇所に対する重複したsuggestを防止するため
  - 条件
    - 同一filePath + 同一originalCodeのsuggestは重複として拒否する
    - 重複チェックは現在のセッション内のsuggestのみが対象（以前のsuggestはAgentに伝えない）
  - 結果(アクション)
    - 重複するsuggestの登録を拒否し、エラーメッセージを返す
  - 関連するユースケースorエンティティ: Suggestion, storeSuggestTool

- サジェスト行数上限ルール
  - 目的/背景
    - GitLab APIの制約およびレビューの可読性を確保するため
  - 条件
    - originalCodeが201行を超える場合は登録を拒否する
  - 結果(アクション)
    - 行数超過のsuggestの登録を拒否し、エラーメッセージを返す
  - 関連するユースケースorエンティティ: Suggestion, storeSuggestTool

- サジェスト自動resolveルール
  - 目的/背景
    - 古いsuggestや新しいsuggestと重複するsuggestが残り続けることを防止するため
  - 条件（以下のいずれかに該当するsuggest discussionが対象）
    - diff更新済みのsystem noteが存在する（即座にresolve）
    - 現在のチェックリストに含まれないチェック項目のsuggestである（即座にresolve）
    - 新しいsuggestと行範囲が1行でも重複する（overlap判定によるresolve）
    - 以前のsuggestの行番号解決に失敗した（コードがdiffに存在しない → resolve）
  - 結果(アクション)
    - 該当するsuggest discussionを自動でresolveする
  - 関連するユースケースorエンティティ: SuggestDiscussion, ReviewExecutionService, SuggestOverlapResolver, CommentPostingService

- サジェストoverlap判定ルール
  - 目的/背景
    - 以前のsuggestと新しいsuggestが同じ行範囲に対するものである場合、以前のsuggestをresolveして新しいsuggestに置き換えるため
    - Agentには以前のsuggestを伝えず、最新のdiffに基づいて自由にsuggestを生成させる
  - 条件
    - 以前のsuggestのoriginalCodeをDiffBasedSuggestionLineResolverで行範囲に解決する
    - 新suggestの行範囲（newLine - linesAbove 〜 newLine + linesBelow）と以前suggestの行範囲を比較する
    - 同一ファイルで startA <= endB && startB <= endA の場合に重複と判定する
  - 結果(アクション)
    - 行範囲が重複する以前のsuggest discussionをresolve対象に追加する
    - 行範囲が重複しない以前のsuggestはそのまま残す
  - 関連するユースケースorエンティティ: SuggestOverlapResolver, ReviewExecutionService

- AIレビュー方針ルール
  - 目的/背景
    - レビュー結果がノイズになるとユーザの認知負担を増やしレビュー結果への信頼を損なうため、対象外項目は無理にレビューしない
    - 細かい指示を毎回与えなくてもベストプラクティスに沿ったレビューを行わせる
  - 条件
    - チェック項目の要件がdiffの変更内容に対して評価対象外（無関係）と判断される場合
    - それ以外の場合は通常通りレビューを実施する
  - 結果(アクション)
    - 評価対象外の場合: ユーザ定義の評定リスト内に out-of-scope（該当なし／評価対象外）相当の評定があればそれを優先利用、なければ予約フォールバックラベル `-` を選び、コメントで対象外である旨と理由を明示する
    - 予約フォールバックラベル `-` は ReviewSettings.ratings に含まれていなくても storeReviewResult / CommentParser / ReviewSettings の3箇所で常時受理される
    - レビュー実施時はコード/ドキュメントレビューのベストプラクティスに沿う
  - 関連するユースケースorエンティティ: reviewAgent, ReviewSettings, Rating, storeReviewResultTool, CommentParser

- サジェスト行番号解決ルール
  - 目的/背景
    - Agentが生成したコード断片からGitLab APIのdiff discussion投稿に必要なposition情報を算出するため
  - 条件
    - suggestのoriginalCodeをMR diffから検索し、該当箇所の行番号を特定する
  - 結果(アクション)
    - ResolvedSuggestion（newLine, linesAbove, linesBelow, oldPath, newPath）を算出する
    - 該当箇所が見つからない場合はエラーとして扱い、当該suggestをスキップする
  - 関連するユースケースorエンティティ: ResolvedSuggestion, CommentPostingService
