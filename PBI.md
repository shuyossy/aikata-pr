# ID: 1
- PBI名: SSE接続断に対する耐性強化
- ステータス: done（指摘事項2回目対応として、SSEを廃止しジョブ作成+ポーリング方式へ構造変更）
- 指摘事項対応（2回目）の概要:
  - **SSEを完全廃止し、`POST → JSON {jobId} 即時応答` + `GET /api/v1/jobs/{jobId} ポーリング` の2エンドポイント構成に変更**
  - 根本原因の有力仮説: HAProxy配下で同じ環境を使う別アプリ（`/api/sse/...` パスの Next.js）は問題なく動作する一方、aikata-pr の `/api/v1/review` への長時間SSE接続はHAProxyで終端され、レスポンス全体がHAProxyのstatsページHTMLに置き換わる事象が発生。HAProxy設定でパスベースのSSE特殊扱い（長timeout・バッファリング無効）が `/api/sse/` 系のパスにのみ適用されている可能性が高い
  - SSEの長時間接続を捨てて、軽量JSON応答 + ポーリングに切り替えることで、HAProxy/プロキシの設定や挙動に依存しない構造を実現
  - 主要変更:
    - APIサーバ: `POST /api/v1/review` / `POST /api/v1/pipeline-report` をJSON応答化し、AI処理は `runBackgroundJob` で fire-and-forget 起動。pending同期保存（保存失敗で500、AI処理開始しない）。`PendingJobResultRecord` に `currentStep` フィールドを追加してポーリング進捗を伝える
    - CLI: `ReviewApiClient` / `PipelineReportApiClient` から `parseSSEStream` を削除。`X-Request-Id` をCLIが事前生成してヘッダ送信（プロキシでレスポンスが改変されてもjobIdは手元にある）。Content-Type 検証で非JSON応答を即時失敗扱い。`pollJobResult` でポーリング、`currentStep` をCIログに流す
    - 環境変数: `SSE_IDLE_TIMEOUT_MS` を削除
  - 並行アクション: HAProxy運用担当者へ `/api/v1/review` / `/api/v1/pipeline-report` のSSE特殊扱いを確認・依頼することを推奨（アプリ側は本対応でHAProxy設定への依存を構造的に下げているが、運用側の設定見直しも望ましい）
- 過去の対策（前回 commit: `1f2d824`）:
  - SSEパーサー共通化＋robust化（CRLF/LF両対応・複数行data結合等）。共通実装: `src/infrastructure/adapter/httpClient/sseParser.ts`
  - APIサーバが`event: meta\ndata: {"jobId": ...}`を最初のSSEメッセージとして送出
  - APIサーバが `X-Accel-Buffering: no` ヘッダを付与
